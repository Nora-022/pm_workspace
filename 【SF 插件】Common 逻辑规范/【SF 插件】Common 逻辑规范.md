**【SF 插件】Common 逻辑规范**

1\. **文档定位与适用范围**

1.1 **文档定位**

本规范用于定义 StreamFab 浏览器插件的 **通用逻辑规则与系统行为约束**。

Common 文档用于描述：

插件生命周期的固定结构；

各核心模块的统一行为规则；

所有插件必须遵循的系统级约束。

插件差异通过[【SF
插件】能力声明表规范（V1.0）](https://i6a1sqw3p2.feishu.cn/docx/YIlEdriLZoqjusxzJvvclIHLnaf?from=from_copylink)进行声明，并在插件需求文档中展开。

1.2 **适用范围**

本规范适用于所有 StreamFab 浏览器插件，包括但不限于：

单站点插件；

多站点插件；

试用与订阅插件。

所有插件在设计与实现时，必须遵循本规范中定义的逻辑与约束，不得自行修改或绕过。

1.3 **文档分层关系**

**Common 逻辑规范**  
定义系统固定流程与不可变规则。

**能力声明表**  
用于声明插件在 Common 规则下的能力参数与策略选择。

**插件需求文档**  
在 Common 与能力声明约束下，定义具体的产品交互与功能设计。

1.4 **约束原则**

Common 文档不定义 UI 表现、交互细节或文案内容；

Common 文档不约束具体技术实现方式；

所有系统级行为，如未在能力声明中明确为可变项，均视为通用规则。

2\. **插件运行周期与数据生命周期**

2.1 **插件运行周期**

插件的运行周期以**浏览器启动到浏览器关闭**为边界。

在一次浏览器运行周期内，插件保持持续运行状态，页面刷新、页面跳转或站点切换，不会中断插件运行周期。

2.2 **数据保留规则**

在一次浏览器运行周期内，插件产生的数据持续保留，包括但不限于：

视频检测结果；

视频分析结果；

下载任务及其状态记录。

上述数据不会因页面刷新、页面跳转或站点切换而被自动清除。

2.3 **数据清除规则**

插件运行期间产生的数据，仅在以下情况下被清除：

用户主动执行清除缓存操作；

浏览器被关闭并重新启动。

除上述情况外，插件不得自动清除检测数据、分析结果或下载记录。

2.4 **Detection Session 与数据关系**

插件可在运行周期内维护一个或多个 Detection
Session，用于组织检测与分析过程。

Detection Session 的结束不等同于数据清除；

不同 Detection Session 之间的数据相互隔离；

当用户回到原有 Detection Session 时，该 Session 内的数据仍然存在。

2.5 **多站点数据隔离**

当插件支持多个站点时：

不同站点的数据相互隔离；

一个站点内的检测、分析与下载数据，不得影响其他站点。

3\. **插件状态机与生命周期流程**

3.1 **状态机定义**

插件在运行周期内遵循统一状态机，用于约束插件在不同阶段的系统行为。

状态机描述的是逻辑阶段，不等同于页面或 UI 展示状态。

3.2 **状态机基本流程**

初始化（Initialization）

站点登录（Site Login）

授权（Authorization）

视频检测（Detection）

视频分析（Analysis）

下载任务创建（Task Creation）

下载执行（Download Execution）

结果反馈（Result Feedback）

3.3 **站点登录规则**

是否要求站点登录，由具体流媒体站点与场景决定；Common
不将“站点登录”定义为绝对强制或绝对可跳过。

当站点处于未登录且该场景要求登录时，插件不得进入后续可用流程（检测/分析/下载）。

3.4 **授权规则（强制）**

所有插件均必须完成用户账号授权后才可使用。

未授权状态下，插件不可进入可用流程（检测/分析/下载）。

3.5 **授权失败处理规范**

授权失败类型统一分为：

网络错误

授权上限

其它错误

授权失败时，先展示一个自动消失的全局 Toast（一句简短提示）。

同时在插件弹窗内展示失败原因与可行解决方式（例如重试 / 联系客服）。

3.6 **授权失败与数据清空规则（强制）**

授权失败后，插件不保留任何检测/分析/下载相关信息。

用户退出登录后，插件内与该用户相关的信息清空。

4\. **试用权益规则**

插件试用权益同时受 **有效期** 与 **可用次数** 两个条件约束；

两个条件 **并行生效，任一条件不满足，试用权益即视为失效**。

4.1 **试用有效期规则**

插件试用权益存在固定有效期；

试用有效期自用户首次激活插件之日起计算；

试用有效期为 **30 天**；

当试用有效期结束后：

即使用户仍剩余可用试用次数；

试用权益仍视为失效，用户不可继续使用试用功能。

4.2 **试用次数规则**

插件试用权益包含固定数量的可用下载次数；

不同类型插件的试用次数策略不同：

对于 **单站点、DRM 加密类插件**，试用次数较少；

对于 **多站点、非 DRM 类插件**，试用次数相对较多；

具体试用次数由插件能力声明表进行声明。

4.3 **试用期内功能范围说明**

在试用权益有效期间内：

用户可体验插件的全部功能；

不对插件功能能力做限制；

仅对下载次数等使用额度进行限制。

5\. **视频检测逻辑规范**

5.1 **检测定义**

视频检测用于识别当前站点环境中可用于后续分析与下载的视频内容。

检测行为仅发生在**已完成授权**的前提下。

5.2 **检测触发规则**

视频检测在用户访问支持的站点或页面时触发；

检测行为不依赖用户是否具备可用下载额度；

未完成授权时，不允许进行视频检测。

5.3 **检测范围**

视频检测仅在插件支持的站点范围内生效；

非支持站点不参与检测流程。

5.4 **检测结果管理**

在一次插件运行周期内，插件可维护多个相互独立的检测过程；

每个检测过程内产生的视频检测结果仅在该检测过程范围内生效；

不同检测过程之间的检测结果相互隔离。

5.5 **检测结果的生命周期**

检测结果在当前浏览器运行周期内持续保留；

检测结果不会因页面刷新、页面跳转或站点切换而自动清除；

检测过程的结束不等同于检测结果的清除。

5.6 **检测与后续流程关系**

视频检测仅用于发现视频资源；

检测完成后，需进入视频分析流程；

未完成分析的视频，不允许进入下载任务创建流程。

6\. **视频分析（Analysis）逻辑规范**

6.1 **分析定义**

视频分析用于获取创建下载任务所必需的视频信息。

分析行为基于已完成的视频检测结果进行。

6.2 **分析触发规则**

视频分析仅在检测到视频内容后触发；

分析行为仅发生在已完成授权的前提下；

未完成授权时，不允许进行视频分析。

6.3 **分析形态规范**

插件的视频分析支持以下两种通用形态：

**直接分析**

**分阶段异步分析**

具体采用哪一种分析形态，由插件能力声明约定。

**直接分析**

对视频执行一次性分析流程；

分析完成后，直接产出创建下载任务所需的信息。

**分阶段异步分析**

分阶段执行分析流程；

预分析阶段用于建立视频基础信息；

后续分析阶段用于补齐可下载所需的完整信息；

在完整分析完成之前，不允许创建下载任务。

6.4 **分析结果管理**

分析完成后，生成对应的视频分析结果；

分析结果在当前浏览器运行周期内持续有效；

分析结果不会因页面刷新或站点切换而自动失效。

6.5 **分析与下载的前置关系（强制）**

下载任务的创建必须基于已完成的视频分析结果；

在视频分析未完成之前，系统不允许创建任何下载任务。

6.6 **分析失败处理**

对于不支持下载的视频，应在检测阶段完成识别并不进入后续分析流程。

分析过程中若未能获得可用于下载的必要信息，则不创建下载任务。

允许用户通过重新加载当前页面触发再次检测与分析；不提供针对单个视频的手动重试入口。

7\. **下载任务创建与管理**

7.1 **下载任务定义**

下载任务用于描述一次完整的视频下载执行过程。

每个下载任务对应一个具体的视频资源。

7.2 **任务创建前置条件**

下载任务的创建必须基于已完成的视频分析结果；

未完成视频分析，不允许创建下载任务；

未完成授权状态下，不允许创建下载任务。

7.3 **任务创建与额度校验**

下载任务创建前，系统需对用户当前可用下载额度进行校验；

下载额度仅在任务创建阶段生效，不影响视频检测与视频分析。

**任务创建规则：**

当用户本次选择的视频数量小于或等于当前可用下载额度时，创建全部下载任务；

当用户本次选择的视频数量大于当前可用下载额度且可用额度大于零时，仅按选择顺序创建不超过可用额度数量的下载任务，其余不创建；

当当前可用下载额度为零时，不创建任何下载任务，并触发对应的额度提示。

7.4 **下载任务状态**

下载任务具有以下状态：

Pending：任务已创建，等待执行；

Downloading：任务正在执行中；

Completed：任务执行完成；

Failed：任务执行失败。

7.5 **下载列表展示分区说明**

下载列表按展示分区进行划分：

**Downloading
分区**：用于展示尚未完成的任务，包括下载中任务与下载失败任务；

**Downloaded 分区**：用于展示已成功完成的下载任务。

展示分区用于 UI 展示，不等同于下载任务状态。

7.6 **Retry 规则**

Retry 行为仅适用于状态为 Failed 的下载任务；

Retry 不受并发下载限制；

Retry 行为受单日下载额度限制；

Retry 失败时，任务可能快速再次失败。

7.7 **下载任务与登录状态**

下载过程中用户退出站点登录状态时：

禁止创建新的下载任务；

已创建及下载中的任务不受影响，继续执行。

7.8 **下载额度扣减规则**

下载额度采用**两阶段处理机制**：占用与确认扣减；

所有插件统一遵循以下规则：

**额度占用时机**

在下载任务创建成功时，占用 1 次下载额度；

占用仅表示额度被暂时锁定，不视为真实扣减。

**额度确认扣减时机**

当下载任务成功完成后，占用的额度转为真实扣减；

成功完成的判定以插件侧“下载成功状态”为准。

**额度释放规则**

若下载任务在执行过程中失败、取消或异常终止；

已占用的下载额度必须被释放，不产生实际扣减。

7.9 **下载额度扣减规则**

下载额度的扣减时机由插件能力声明约定；

支持在以下时机进行扣减：

下载任务创建时；

下载任务成功完成后。

8\. **下载执行与 CoApp 交互**

8.1 **本地执行职责**

下载任务的实际执行由本地组件（CoApp）负责完成。

插件负责创建与管理下载任务，不直接执行具体的下载行为。

8.2 **执行触发规则**

下载任务创建完成后，插件将任务交由本地组件执行；

本地组件根据任务状态驱动下载执行流程。

8.3 **执行状态反馈**

本地组件需向插件反馈下载任务的执行状态；

插件根据反馈更新下载任务状态与展示信息。

8.4 **并发与队列规则**

同时可执行的下载任务数量由插件能力声明约定；

超出并发限制的任务进入等待状态，按顺序执行。

8.5 **本地路径与设置生效规则**

下载相关设置的变更不影响已创建、队列中或已完成的下载任务；

设置变更仅对后续新创建的下载任务生效；

日志路径的变更需重启本地组件后生效。

8.6 **执行失败处理**

下载执行失败时，任务状态更新为 Failed；

失败任务的后续处理遵循下载任务管理与 Retry 规则。

9\. **CoApp 安装引导的系统环境限制规范**

9.1 **环境识别规则**

插件在展示 CoApp
安装入口或安装引导界面前，**必须识别当前操作系统类型**；

操作系统识别结果作为 CoApp 可用性判定的前置条件。

9.2 **MacOS 系统限制规则**

当识别到当前操作系统为 **MacOS** 时：

视为 **CoApp 当前阶段不可用环境**；

插件 **不得引导用户继续执行 CoApp 安装或下载流程**；

CoApp 下载按钮处于 **不可用状态；**

9.3 **不可用状态提示规范**

当 CoApp 因操作系统限制处于不可用状态时：

插件必须向用户提供明确的不可用原因提示；

**中文提示：**

|                              |
|:-----------------------------|
| MacOS 系统暂不可用，感谢支持 |

**英文提示：**

|                                        |
|:---------------------------------------|
| MacOS unavailable, thanks for support. |

提示的具体承载形式（如
hover、tooltip、说明文本等）不作限定，但必须确保用户可感知。

9.4 **规则归属说明**

MacOS 下 CoApp 不可用属于 **系统级固定限制**；

该限制 **不受插件能力声明表影响**；

10\. **异常与边界处理逻辑规范**

10.1 **不支持站点处理**

当用户访问插件不支持的网站或场景时，插件不进入检测与分析流程；

插件需按照插件能力声明约定的方式进行处理：

直接提示当前网站不支持；

或引导用户使用桌面端产品继续操作。

10.2 **授权异常处理**

授权异常包括：

网络错误；

授权上限；

其它错误。

授权异常发生时，插件需展示自动消失的全局提示；

插件内部需提供查看授权异常原因及解决方式的入口。

10.3 **下载异常处理**

下载执行过程中发生异常时，下载任务状态更新为 Failed；

下载失败的任务展示在 Downloading 分区中；

下载失败任务遵循统一的 Retry 规则。

10.4 **登录状态异常**

下载过程中用户退出站点登录状态时：

禁止创建新的下载任务；

已创建及下载中的任务不受影响，继续执行。

10.5 **异常处理约束**

异常处理仅影响对应异常场景，不得影响其他正常流程；

插件不得通过异常路径绕过授权、分析或额度校验规则。

11\. **任务数据存储分层与状态映射规则**

11.1 **存储空间定义**

插件在运行周期内使用以下存储空间承载任务数据：

**内存（Memory）**：运行期存储，用于临时与高频变化数据；

**SessionStorage**：会话级轻量存储，用于数量受控的关键执行态数据；

**IndexedDB**：本地持久化存储，用于体量较大或生命周期较长的数据。

11.2 **存储分层基本原则**

插件在数据存储层面统一遵循以下原则：

高频变化、运行期数据存储于内存；

数量受控、对当前执行过程关键的数据存储于 SessionStorage；

可增长、需长期保留的任务数据存储于 IndexedDB。

11.3 **下载任务状态判定规则**

插件采用固定并发模型，**并发任务数在不同插件能力之间存在差异**，具体并发能力以能力声明表为准。

当任务进入并发执行队列时，即判定为下载中任务；

下载中任务的判定包含下载初始化阶段；

插件不要求在 Common 层面对下载任务的内部状态进行进一步细分。

11.4 **下载中任务的数据存储规则**

**下载中任务必须存储于 SessionStorage**；

SessionStorage 中下载中任务的数量上限为 **5**；

当任务状态从下载中迁移为完成或失败时，该任务数据应从 SessionStorage
中移除；

非下载中任务不得存储于 SessionStorage。

11.5 **非下载中任务的数据存储规则**

以下任务数据统一存储于 IndexedDB：

下载前任务；

下载完成任务。

IndexedDB
作为任务数据的主要存储空间，其数据规模受浏览器与磁盘环境限制，可通过清理策略控制长期增长。

11.6 **内存使用边界**

内存用于运行期缓存、高频更新数据及计算中间态；

内存不得作为下载前任务或下载完成任务的唯一存储位置；

任务主数据必须在 SessionStorage 或 IndexedDB 中具备明确的存储归属。

11.7 **模块约束边界**

本模块仅约束：

任务状态与存储空间的映射关系；

各类存储空间的职责边界。

本模块不约束：

任务字段结构；

存储实现方式；

下载引擎或任务调度逻辑。

12\. **Dashboard 与设置逻辑规范**

12.1 **Dashboard 定位**

Dashboard 用于集中展示插件的运行状态与用户相关信息，包括但不限于：

当前授权状态；

用户权益与下载额度信息；

下载任务概览。

Dashboard 仅用于信息展示与操作入口，不参与核心流程控制。

12.2 **设置项基本规则**

插件设置用于影响后续行为的默认参数；

设置项不直接改变系统流程结构。

12.3 **设置生效范围**

设置变更不影响以下任务：

已完成的下载任务；

正在执行的下载任务；

已进入队列的下载任务。

设置变更仅对后续新创建的下载任务生效。

12.4 **特殊设置生效规则**

日志路径相关设置的变更，需重启 CoApp 后生效；

其他设置项的生效时机，由插件需求文档明确，但不得违反本章节规则。

12.5 **约束说明**

Dashboard 与设置不得绕过授权、分析或额度校验规则；

设置项不得影响已存在的数据一致性。

13\. **文档约束与扩展说明**

13.1 **Common 的职责边界**

Common 逻辑规范用于定义插件系统的**固定结构与不可变规则**，包括：

插件生命周期的基本流程；

各核心模块的通用行为约束；

系统级的前置条件与禁止规则。

Common 文档不定义具体插件的差异化行为。

13.2 **与能力声明表的关系**

能力声明表用于描述插件在 Common 规则下的能力差异与策略选择；

能力声明表不得修改或覆盖 Common 中定义的流程结构与强制规则；

若某项行为未在能力声明表中声明为可变项，则默认遵循 Common 规则。

13.3 **与插件需求文档的关系**

插件需求文档用于描述具体插件的功能、交互与展示方式；

插件需求文档必须建立在 Common 与能力声明表的约束之上；

插件需求文档不得引入新的系统级流程或绕过 Common 规则。

13.4 **扩展与演进原则**

Common 规则的新增或修改，应以“影响多个插件”为前提；

插件个性化需求不应直接写入 Common；

当多个插件出现相同的新规则需求时，方可考虑上收至 Common。

13.5 **约束总则**

所有插件必须遵循 Common 逻辑规范；

能力声明表与插件需求文档均不得与 Common 产生逻辑冲突；

若发生冲突，应以 Common 逻辑规范为准。
