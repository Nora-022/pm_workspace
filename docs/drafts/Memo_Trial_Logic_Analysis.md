# 试用扣减逻辑深度分析：任务发起 vs. 任务完成

## 1. 核心差异对比

| 维度 | A. 任务发起就扣减 (Deduct on Start) | B. 任务下载完成才扣减 (Deduct on Success) |
| :--- | :--- | :--- |
| **扣减时机** | 用户点击“开始下载/分析”瞬间 | 进度条走到 100% 且文件生成成功瞬间 |
| **用户感知** | “我买了张票，进场了” | “我拿到货了，付钱” |
| **技术复杂度** | 低（原子操作，点击即扣） | 高（需处理回调、超时、部分成功等状态） |
| **业务风险** | 容易被投诉（没下成功也扣了） | 容易被薅羊毛（如下载了99%断网，实际已拿到部分数据） |

## 2. 你的假设分析
> **你的观点：** “针对第一种，如果下载失败重试不扣减，那是不是也就约等于第二种逻辑了？”

**结论：** **虽然结果接近，但本质完全不同（Not Equivalent）。** 它们在**用户体验心理**和**技术边界处理**上存在巨大鸿沟。

### 为什么“失败返还” ≠ “成功才扣”？

#### (1) 心理账户差异 (The Psychological Gap)
*   **方案 A (发起扣 + 失败退):**
    *   用户心理：我先付了钱。如果失败了，我得**盯着你退钱**。如果系统没退（Bug 或网络延迟），我会非常愤怒。
    *   *焦虑点：* “我的次数回滚了吗？”
*   **方案 B (成功扣):**
    *   用户心理：我不花钱先试。成功了你再扣，我心甘情愿。
    *   *爽点：* 无风险尝试。

#### (2) 边界场景差异 (Edge Cases)

| 场景 | 方案 A (发起扣 + 失败重试免费) | 方案 B (成功才扣) |
| :--- | :--- | :--- |
| **场景 1: 任务卡死 (Pending)** | 此时次数已扣。用户看到进度条不动，想刷新。**结果：用户不敢刷新，怕重试判为新任务又扣一次。** | 次数未扣。用户随意刷新重试。**体验更佳。** |
| **场景 2: 分析成功但下载失败** | 已扣费。用户获得了“分析结果”但没拿到文件。**争议点：算成功还是失败？** | 未扣费。平台亏损了计算资源（分析已跑完），但没收到钱。 |
| **场景 3: 恶意并发** | 用户同时开10个窗口点开始。**系统立刻扣10次，余额不足直接拦截。** (防刷好做) | 用户开10个窗口。系统都放行了，最后结算时发现余额只够扣1次。**这就产生了“透支”风险。** |

## 3. 建议方案
对于 **RecordFab/Dvdfab** 这种如下载/转换类的工具产品：

### 推荐：改良版方案 A (预冻结模式)
单纯的“发起扣”太霸道，单纯的“成功扣”技术坑太多（透支、状态同步）。
建议采用 **“预占用 (Freeze) -> 结算 (Settle) / 释放 (Release)”** 机制：

1.  **点击开始：** 并不真扣，而是**冻结** 1 次试用额度。（前端显示：剩余 2 次，冻结 1 次）。
2.  **任务进行中：** 该额度不可用于其他任务。
3.  **任务成功：** 将“冻结”转为“已消费”。
4.  **任务失败/取消：** 解冻，额度退回。

**优势：**
*   解决了方案 B 的“透支风险”（没额度没法冻结）。
*   解决了方案 A 的“用户焦虑”（明确告知是冻结，失败会自动解冻）。
