**本文定位**：本文不是直接给出最终拍板结论，而是把 RecordFab 若做"云端直播录制"需要建设的链路、能力、成本、风险和待验证问题摆清楚，供研发和事业部评审。

## 一、背景与目标

### 1.1 背景来源

已有用户明确反馈过定时录制需求，希望产品可以在直播开始时自动录制，减少人工值守。此前产品相关调研显示，直播前后 URL 变化对 RecordFab 的流拦截录制方式影响有限，真正难点在于直播等待、播放触发、流检测、录制持续和结束判断。

来源：[直播前后 URL 变化调研](https://i6a1sqw3p2.feishu.cn/docx/TVcodd5BCoX5Pextp2Bcyt85nGd)

市场调研文档也提到云端直存、本地挂机录制 + 自动云同步等方向，说明用户不仅有"录下来"的需求，也有跨设备访问、手机端观看和减少本地设备依赖的诉求。

来源：[云上直播录制功能及市场潜力调研](https://i6a1sqw3p2.feishu.cn/wiki/K7OXwBvG0i1iw0kgE74cAiXZnOd)

### 1.2 目标定义

把"云上直播录制"定义为：

- 用户不再依赖本地 PC 持续运行 RecordFab。
- 录制执行发生在 RecordFab 云端。
- 用户通过 RecordFab 提供的入口（本地客户端 / 浏览器扩展 / Web 控制台等）进入直播间并触发录制。
- 云端持续录制直播，直到用户停止、直播结束或触发兜底规则。
- 录制结果进入云端文件库，用户可跨设备下载或播放。

这一定义下，本地客户端、浏览器扩展、Web 控制台或手机 App 都只是控制入口；真正关键的是 RecordFab 是否具备稳定的云端录制执行能力。

## 二、PlayOn 的参考价值：架构可借鉴，场景不能照搬

### 2.1 PlayOn Cloud 的架构抽象

来源：[PlayOn 云端 DVR 录制产品深度分析](https://i6a1sqw3p2.feishu.cn/docx/ViS3di6KaocPDQxCm23cWCpsnof)、[PlayOn 产品发展趋势](https://i6a1sqw3p2.feishu.cn/wiki/OWXgwOCYFiHaEHkCnT2csXSinod)

PlayOn Cloud 可以抽象为四层能力：

| 层级 | PlayOn Cloud 的作用 | 对 RecordFab 的参考价值 |
| --- | --- | --- |
| 用户控制入口 | 用户通过 App 选择内容、发起录制、查看录制结果 | RecordFab 也需要一个跨端入口，用于连接云端、触发录制、查看结果 |
| 云端执行环境 | 云端虚拟环境代替用户完成播放和录制 | RecordFab 可借鉴录制执行上云的架构，不再依赖用户本地 PC |
| 录制流水线 | 云端播放内容、录制、封装、生成文件 | RecordFab 需要把现有录制能力迁移或重构到云端环境中 |
| 云端文件交付 | 录制完成后，用户跨设备下载或观看文件 | RecordFab 需要建设云端文件库、保留策略、下载入口和通知机制 |

### 2.2 不能照搬 PlayOn 的原因

PlayOn 的核心场景主要是 VOD 点播内容，而 RecordFab 当前讨论的是直播录制。二者在任务性质上差异很大：

| 维度 | VOD 云端录制 | 直播云端录制 |
| --- | --- | --- |
| 内容状态 | 内容已存在，通常可立即播放 | 内容可能未开播、直播中、已结束或临时取消 |
| 开始条件 | 用户选择内容后即可执行 | 需要进入直播间并等待直播流出现 |
| 时长 | 通常有明确总时长 | 通常无固定总时长 |
| 结束判断 | 可参考播放时长或播放完成状态 | 需要结合用户停止、直播结束标识、断流、无数据超时、最长录制时长 |
| 并发特征 | 任务时间相对分散 | 热门直播可能在同一时间集中开播，形成并发峰值 |
| 失败原因 | 平台兼容、播放失败、录制失败 | 还包括延迟开播、取消开播、直播中断、主播临时下播、直播间状态变化 |
| 用户价值 | 离线观看、归档 VOD 内容 | 防错过直播、无人值守、保存限时内容、跨设备查看结果 |

因此，RecordFab 应借鉴 PlayOn 的云端执行架构，而不是照搬 PlayOn 的 VOD 业务闭环。文档后续讨论应围绕"云端如何完成直播录制"展开。

### 2.3 PlayOn 路径选择的时代约束

PlayOn Cloud 在 2016 年上线时选择"云端浏览器 + 屏幕录制 + 移动 App"，与当时的技术与市场环境相关：

- Web 像素流技术尚未成熟，浏览器扩展能力受限
- 移动端是增量市场，"用手机控制录制"是关键差异化卖点
- 浏览器扩展商店生态尚未完全成熟

到 2026 年，浏览器扩展能力已大幅增强（`chrome.webRequest`、`declarativeNetRequest` 等 API），扩展商店分发成熟，移动端已不是稀缺入口。这意味着 PlayOn 选择的路径在今天不一定是唯一选项——可以照搬实现路径（路径 A1），也可以基于现有扩展能力走更轻量的路径（路径 A2）。

本文在第三章并列展开两条候选路径，让评审在了解技术路径差异、工程量差异、可行性差异后选择。

## 三、RecordFab 云上直播录制的目标链路

云上直播录制的产品定位是统一的（用户不依赖本地设备 + 录制执行在云端 + 跨设备访问结果），但具体技术实现有两条候选路径。本章按 A1 / A2 分别展开主路径与差异点，自动化能力边界放在 3.3。

### 3.1 路径 A1：云端浏览器直播录制

更贴近 RecordFab 既有产品形态的主路径不是让用户先填写复杂的 URL、开播时间和等待时长，而是提供一个云端浏览器录制会话，让用户像使用本地 RecordFab 一样操作网站。

```
① 用户进入 RecordFab 云端浏览器入口
   入口可以来自桌面客户端、Web 控制台或手机 App。
   入口的职责是连接云端浏览器会话，而不是在本地执行录制。

② RecordFab 分配云端浏览器会话
   为用户创建隔离的云端浏览器 / 虚拟桌面环境。
   用户可在该环境中打开目标直播网站。

③ 用户自行完成登录并进入直播间
   第三方账号登录、地区校验、直播间选择由用户在云端浏览器中完成。
   RecordFab 不需要在首期建设节目单或内容目录。

④ 用户点击 RecordFab 录制按钮
   云端录制控制器开始监听直播流。
   如果直播已经开始，检测到流后立即开始录制。
   如果直播尚未开始，进入等待状态。

⑤ 云端执行实时录制
   录制执行发生在 RecordFab 云端。
   用户可关闭本地设备或退出控制入口，云端录制继续运行。

⑥ 云端处理直播状态变化
   包括延迟开播、断流、恢复、主播下播、用户手动停止、无数据超时和最长录制时长兜底。

⑦ 录制完成后生成文件
   云端完成封装 / 转码 / 文件校验，生成可交付文件。

⑧ 文件进入 RecordFab 云端文件库
   用户可跨设备查看任务状态、下载文件、播放文件或删除文件。

⑨ 系统通知用户结果
   成功、失败、异常中断、文件可用期、下载入口等通过桌面通知、邮件或 App Push 触达。
```

### 3.2 路径 A2：浏览器扩展 + 云端录制服务

路径 A2 是 PM 侧在 A1 基础上提出的备选思路。核心想法是：不在云端起浏览器，改由用户本地浏览器承担"页面浏览与流地址识别"的工作，云端只承担"拉流 + 录制 + 文件交付"的工作。

3.2.1 主路径

```
① 用户在本地浏览器（Chrome / Edge）安装 RecordFab 扩展
   扩展通过浏览器扩展商店分发，零额外本地组件安装。

② 用户在本地浏览器中正常访问目标直播站点
   登录、进入直播间等操作全部在用户本地浏览器完成。
   本地浏览器已具备的 IP、cookie、地区都被自然使用。

③ 用户在直播间点击 RecordFab 扩展按钮
   扩展拦截当前页面直播流地址（HLS m3u8 / DASH manifest）。
   扩展提取必要的认证信息（cookie、Authorization header、Referer 等）。

④ 扩展将任务提交到 RecordFab 云端
   提交内容：流地址 + 认证信息 + 任务元数据（站点、用户、画质偏好）。
   提交后用户即可关闭浏览器或电脑。

⑤ 云端录制服务接收任务并主动拉流
   云端 FFmpeg（或类似工具）直接以 HTTP 请求方式拉取 manifest 和分片。
   不依赖浏览器播放行为，纯粹的服务端 HTTP 客户端行为。

⑥ 云端处理直播状态变化
   包括 manifest 滚动、token 续期、断流恢复、用户停止指令、最长录制时长兜底。

⑦ 录制完成后生成文件并入云端文件库
   云端封装 / 校验后生成可交付文件。

⑧ 通知用户结果
   通过桌面通知、邮件、扩展提示等触达。

⑨ 用户跨设备下载或在线播放
   任意设备打开 Web 控制台或扩展即可访问云端文件库。
```

3.2.2 路径 A2 与 A1 的关键差异

| 维度 | A1 云端浏览器 | A2 扩展 + 云端服务 |
| --- | --- | --- |
| 云端是否需要浏览器实例 | 必须 | 不需要 |
| 像素流通道 | 必须（用户看云端画面） | 不需要 |
| 输入注入通道 | 必须（用户操作云端） | 不需要 |
| 本地组件 | 客户端（或 Web 控制台） | 仅浏览器扩展 |
| 用户登录目标站点的环境 | 云端浏览器 | 用户本地浏览器（IP/cookie/地区均已具备） |
| 单路录制成本 | 高（VM + 浏览器 + 编码 + 像素流） | 低（仅录制进程） |
| 用户启动门槛 | 装客户端 / 等待会话分配 | 扩展商店一键安装 |
| 移动端访问 | 需 App 或 Web | 录制结果可通过 Web 跨设备访问；录制发起需 PC 浏览器 |

3.2.3 RecordFab 现有技术架构关联背景

按 RecordFab 现有技术实现文档（来源：[《RecordFab 录制模式接口文档》](https://i6a1sqw3p2.feishu.cn/wiki/A1F4wDxyxivlLnk006KcMfKAnJf)）：

- 录制引擎核心接口为 `IRecorder`，通过 `RegisterBrowser(QCefWebView* page)` 与 CEF 实例绑定。
- 录制方式是"流拦截 + Remux"：在 CEF 网络层拦截 HLS / DASH 分片（TS / fMP4），分片重新封装为 MP4，**非屏幕录制、非重编码**，输出无质量损失。
- 录制依赖 CEF 实际播放产生的实时数据流——视频必须在 CEF 内播放才能拦截到分片。
- 5x 录制速度的本质：CEF 以 5x 速度播放，分片以 5x 速度产生并被拦截。

这套架构是为本地客户端 + 用户主动播放场景设计的。**路径 A2 设想的"FFmpeg 主动拉流"是一条与现有架构完全不同的技术路径**。

| 维度 | 现有客户端（CEF 播放拦截） | 路径 A2 设想（云端主动拉流） |
| --- | --- | --- |
| 触发方式 | 用户播放视频，分片产生即被拦截 | 服务端主动请求 manifest 和分片 |
| 是否依赖播放行为 | 是 | 否 |
| 实现位置 | CEF 网络层 hook | 云端独立进程 |
| 数据来源 | CEF 播放器产生的实时分片 | HTTP 主动请求获取的分片 |
| 反检测特性 | 真实播放行为，规避部分风控 | 无浏览器签名，需 cookie / header 模拟 |
| 适用场景 | 单机 + 用户主动操作 + 本地录制 | 服务端长任务 + 直播录制 |

A2 设想中"现有 RecordFab 录制能力部分可复用"这一点（如 Remux 算法、结束检测逻辑），**能否在脱离 CEF 上下文的独立环境中编译与运行，需研发调研后才能给出结论**。本节信息源为 RecordFab 内部技术文档，技术可行性不在本文范围内下定论。

3.2.4 路径 A2 的 PM 侧考虑

A2 作为备选思路的产品形态优势：

- **开发与维护成本**：相对独立 App，浏览器扩展形态的开发、上架、维护成本更低，无需独立的双端（iOS / Android）研发与发版流程。
- **复用 StreamFab 扩展产品线经验**：StreamFab 已有的浏览器扩展架构（扩展 + CoApp 双层）已经验证。A2 思路本质是把 CoApp 的角色从"本地"换成"云端"，扩展层的开发框架、UX 规范、流地址识别能力、跨浏览器兼容、上架流程都可复用。
- **用户体验**：用户在自己平时使用的浏览器内操作，登录态、IP、地区都已就绪，免去云端登录、地区校验、风控触发等环节。启动门槛低于客户端形态。
- **跟现有产品线的协同**：StreamFab 浏览器扩展（下载方向）+ RecordFab 浏览器扩展（直播录制方向）可形成对称的扩展产品线，对外叙事一致。

A2 的限制与不确定性：

- **录制范围受限**：仅适用于无 DRM 的直播流。DRM 加密内容云端无 key 无法解密，需另行评估。
- **技术可行性需研发评估**：3.2.3 中的技术路径差异决定了"引擎搬云端"不是简单移植，需要研发明确评估"现有录制能力剥离 CEF 后云端独立运行"的可行性、工程量与潜在替代方案。
- **服务端拉流的反检测能力**：从云端 IP 主动拉直播流，是否触发目标平台的服务端访问风控，需要研发实测。

### 3.3 自动化能力的边界

URL 预约、开播时间、频道关注、自动开播检测并不是主路径的前置条件，更适合放在后续自动化阶段。本节内容与 A1 / A2 路径选择无关：

| 能力 | 定位 | 是否首期必须 |
| --- | --- | --- |
| 用户在直播间手动触发录制 | 主路径，用户进入直播间后点击录制，云端接管后续录制 | 是，建议作为核心验证对象 |
| URL 预约录制 | 用户保存直播间 URL，到点自动打开并等待开播 | 否，可作为二期自动化能力 |
| 开播时间配置 | 辅助调度云端资源，减少长时间等待 | 否，可在预约录制阶段引入 |
| 频道关注 / 主播关注 | 系统监测频道开播并自动录制 | 否，依赖平台适配和开播检测能力，复杂度更高 |
| 自动云同步 | 录制结果同步到用户个人云盘 | 否，仅是结果访问增强，不改变云端录制主链路 |

这样拆分后，首期评审的重点会更清楚：先判断 RecordFab 是否能提供稳定的云端直播录制能力（无论 A1 还是 A2），再讨论是否进一步做预约录制和频道自动化。

## 四、如果 RecordFab 做，需要建设哪些能力

按选定路径不同，能力建设清单有差异。本章按"产品能力 / 技术能力 / 运营与合规能力"三层组织；技术能力进一步拆为通用、A1 专属、A2 专属。

### 4.1 产品能力（共通）

| 能力 | 需要做什么 | 关键问题 |
| --- | --- | --- |
| 用户入口 | 提供桌面客户端 / Web 控制台 / 浏览器扩展 / 手机 App 入口（按选定路径决定具体形态） | 首期入口形态由所选路径决定；是否需要多端同步状态 |
| 录制任务状态 | 展示等待中、录制中、已完成、失败、中断、文件处理中等状态 | 用户如何理解失败原因；是否支持用户手动停止 |
| 云端文件库 | 管理录制完成后的文件，包括下载、播放、删除、过期提示 | 文件保留多久；是否提供在线播放；下载带宽如何计费 |
| 通知体系 | 任务开始、录制中断、录制完成、文件可下载、文件即将过期等通知 | 桌面通知、邮件、App Push 的优先级 |
| 权益与计费 | 定义云录制额度、并发限制、文件保留期、失败补偿规则 | 按录制时长、录制次数、存储空间还是订阅套餐计费 |

### 4.2 技术能力

4.2.1 路径 A1 专属技术能力

| 能力 | 需要做什么 | 关键问题 |
| --- | --- | --- |
| 云端浏览器 / 虚拟桌面 | 在服务器侧为用户创建隔离浏览器环境 | 浏览器指纹、GPU / 虚拟显示、DRM / HDCP、平台风控 |
| 会话管理 | 支持用户进入、断开、恢复和释放云端浏览器会话 | 用户退出后会话是否继续；空闲多久释放；异常如何恢复 |
| 像素流通道 | 把云端浏览器画面编码后推到本地客户端显示 | 延迟、画质、带宽、断线重连、首屏速度 |
| 输入注入通道 | 把本地客户端的鼠标键盘事件传到云端浏览器 | 操作响应性、坐标精度、特殊键支持 |
| 云端录制控制器 | 在云端浏览器中接收录制指令，监听直播流并触发录制 | 录制按钮、流检测和录制器之间的协同方式 |
| 实时录制与封装 | 云端执行长时间实时录制，完成封装、转码或 Remux | 单路资源成本、长时稳定性、画质、失败恢复 |
| 直播结束判断 | 综合直播结束标识、无数据超时、断流、用户停止、最长录制时长 | 如何避免误停；如何避免无限录制 |
| 云端存储与下载 | 保存录制文件，生成下载链接，控制访问权限和保留周期 | 存储成本、下载带宽、文件生命周期和权限安全 |

4.2.2 路径 A2 专属技术能力

| 能力 | 需要做什么 | 关键问题 |
| --- | --- | --- |
| 浏览器扩展开发 | Chrome / Edge 扩展，含 popup UI、任务管理、流拦截、登录态管理 | 复用 StreamFab 扩展架构能省多少工作量 |
| 直播流地址识别 | 在用户访问的直播间页面拦截 HLS / DASH manifest 地址 | `chrome.webRequest` 能否覆盖目标平台的流协议（含 WebSocket、WebRTC 等场景） |
| 认证信息提取 | 提取 cookie、Authorization、Referer、UA 等用于云端复现请求 | 哪些字段是必需的；token 过期机制；IP 绑定的 token 如何处理 |
| 任务提交与状态同步 | 扩展 ↔ 云端 API 通信，含任务创建、状态查询、取消 | 鉴权方式、跟 DVDFab / RecordFab 现有账号体系打通 |
| 云端主动拉流 | 云端 FFmpeg 或同类工具，以服务端 HTTP 请求方式拉取 manifest 和分片 | 长时间稳定性、断流重连、码率切换跟随 |
| HLS / DASH live 滚动处理 | 直播 manifest 是滚动窗口，需要持续拉取最新片段 | manifest 刷新策略、片段去重、起播位置 |
| 认证态续期 | 长直播过程中 cookie / token 可能过期 | 是否需要扩展持续协助续期；扩展不在线时如何处理 |
| 录制结束判断（拆分） | URL 变更检测由扩展感知；时长 / 无数据超时由云端判断 | 扩展与云端的状态同步机制；用户关闭扩展后的判断兜底 |
| 录制核心逻辑复用评估 | RecordFab 现有 Remux、结束检测等代码能否在脱离 CEF 上下文的云端环境中复用 | 待研发调研后确认 |
| 云端存储与下载 | 同 A1 | 同 A1 |

### 4.3 运营与合规能力（共通，路径差异已标注）

| 能力 | 需要做什么 | 关键问题 |
| --- | --- | --- |
| 平台支持范围 | 明确首期支持哪些直播平台，哪些平台暂不支持 | YouTube Live、Twitch、Kick、TikTok Live 等平台优先级如何确定。**A2 路径仅适用无 DRM 平台** |
| 资源池管理 | 管理云端录制实例、并发、排队、超时和成本 | 高峰并发如何控制；用户排队体验如何设计 |
| 风控与代理 | 处理 IP 风控、验证码、地区限制、账号异常 | 是否需要住宅代理；代理成本是否可承受。**A1 / A2 触发风控的方式不同**：A1 是云端浏览器访问行为，A2 是服务端 HTTP 拉流行为 |
| 用户协议 | 明确用户自行登录第三方网站、录制内容责任和文件保留规则 | 服务端代用户录制的合规边界如何定义 |
| 客服处理 | 建立失败归因、任务日志、补偿和申诉处理机制 | 直播取消、平台失败、云端异常分别如何处理 |

## 五、方案路径对比

### 5.1 候选路径列表

| 编号 | 路径 | 定位 |
| --- | --- | --- |
| **A1** | **云端浏览器直播录制** | **目标路径之一**。借鉴 PlayOn Cloud 完整实现，技术路径与现有 RecordFab 客户端相似 |
| A2 | 浏览器扩展 + 云端录制服务 | PM 侧提出的备选思路。形态与维护成本低，复用 StreamFab 扩展经验，技术可行性待研发评估 |
| B | 客户端定时录制 | 本地阶段验证能力。回应已有定时录制需求 |
| C | 本地录制 + 自动云同步 | 结果访问增强。来源于市场调研 Hybrid Mode 思路 |

A1 是评审的主要对照基线；A2 是备选思路。A1 / A2 并列在"云上直播录制"目标方案下；B 是本地阶段验证能力，独立评估；C 是结果访问增强，不应被包装成云上直播录制主方案。

### 5.2 A1 vs A2 详细对比

| 维度 | A1 云端浏览器 | A2 扩展 + 云端服务 |
| --- | --- | --- |
| 技术路径与现有客户端的关系 | 高度相似（CEF + 流拦截 + Remux） | 完全不同（FFmpeg 主动拉流） |
| 现有 RecordFab 代码复用程度 | 较高（IRecorder 可整体搬运到云端浏览器环境） | 不确定（Remux / 结束检测算法理论可剥离，需研发评估） |
| 云端是否运行浏览器实例 | 是 | 否 |
| 像素流 / 输入注入基础设施 | 必须自建 | 不需要 |
| 用户本地组件 | 客户端（含远程画面渲染、输入采集） | 仅浏览器扩展 |
| 用户启动门槛 | 装客户端 + 等待云端会话 | 扩展商店一键安装 |
| 用户登录第三方站点的环境 | 云端浏览器 | 本地浏览器（已有 IP / cookie / 地区） |
| 单路录制资源成本 | 高（VM + 浏览器 + 编码 + 像素流） | 低（仅 FFmpeg 进程） |
| DRM 内容覆盖 | 可探索（与 PlayOn Cloud 路径一致） | 不覆盖（云端无 key 无法解密） |
| 团队复用 | RecordFab 客户端团队为主 | RecordFab 客户端团队 + StreamFab 扩展团队协同 |
| 工程量预估口径 | 类似新一代客户端项目 | 待研发评估技术可行性后给出 |
| 主要不确定性 | 云端浏览器对 DRM / HDCP / 平台风控的稳定性 | 现有录制能力能否脱离 CEF 在云端独立运行 |

### 5.3 全路径对比

| 路径 | 定位 | 能解决的问题 | 不能解决的问题 |
| --- | --- | --- | --- |
| **A1. 云端浏览器直播录制** | 目标路径之一。借鉴 PlayOn 云端执行架构 + 现有 RecordFab 客户端技术路径 | 用户不依赖本地 PC；云端持续录制；录制完成后跨设备访问；可覆盖 DRM 内容 | 单路成本最高；DRM / HDCP 仍有风险；长时稳定性挑战；合规和运维压力最高 |
| A2. 浏览器扩展 + 云端录制服务 | 备选思路。复用 StreamFab 扩展经验 + 云端主动拉流 | 启动门槛低；单路成本低；无需云端浏览器与像素流；用户本地登录态自然复用 | 仅适用无 DRM 直播流；技术路径与现有客户端不同，移植可行性需研发评估；服务端 IP 风控未知 |
| B. 客户端定时录制 | 本地阶段验证能力。回应已有定时录制需求 | 验证直播等待、自动播放、流检测、结束判断等核心链路 | 录制仍依赖用户本地 PC，不是云上录制 |
| C. 本地录制 + 自动云同步 | 结果访问增强。来源于市场调研 Hybrid Mode 思路 | 改善录制后跨设备访问，降低 RecordFab 存储成本 | 不改变录制执行位置，仍依赖本地 PC，不是目标云端方案 |

### 5.4 本地 / 云端 × VOD / 直播 矩阵

不同路径在 RecordFab 产品矩阵中的定位：

|  | 本地 | 云端 |
| --- | --- | --- |
| **VOD** | CEF 播放拦截（现有客户端） | 暂不规划 |
| **直播** | CEF 播放拦截（现有客户端） + 路径 B 定时录制 | A1 或 A2 |

两条技术路线（CEF 播放拦截 / FFmpeg 主动拉流）不是对错关系，是适用场景不同：

- "CEF 播放拦截"是为本地客户端 + 用户主动播放场景设计的合理选择，规避部分服务端风控，无质量损失。
- "FFmpeg 主动拉流"是云端服务无用户播放行为时的必要选择，反检测特性、token 续期、断流处理等都需要独立设计。

若选定路径 A2，意味着 RecordFab 同时维护两条独立的技术路线：客户端继续用现有"播放拦截"做本地高质量录制，云端用"主动拉流"做直播录制场景。

## 六、阶段验证建议

### 6.1 PoC：先验证云端直播录制是否成立

PoC 不需要先做完整 App、计费和多平台覆盖，重点验证核心链路是否跑通。验证项按选定路径不同有差异：

**A1 / A2 共通验证项**

| 验证项 | 验证内容 | 通过标准 |
| --- | --- | --- |
| 直播流检测 | 在目标平台能识别直播流出现并开始录制 | 至少在 1-2 个目标平台跑通 |
| 用户退出后继续录制 | 用户关闭本地入口后，云端录制不中断 | 录制任务可继续运行至自然结束 |
| 结束判断 | 支持用户手动停止、无数据超时、最长录制时长兜底 | 不出现明显误停或无限录制 |
| 文件交付 | 录制完成后生成文件并可下载 | 文件可播放，时长和内容基本完整 |

**A1 专属验证项**

| 验证项 | 验证内容 | 通过标准 |
| --- | --- | --- |
| 云端浏览器可操作 | 用户可进入云端浏览器，打开直播网站并登录 | 操作延迟可接受，登录流程可完成 |
| 像素流稳定性 | 长时间画面传输不断流、不冻屏 | 1 小时连续操作无显著异常 |

**A2 专属验证项**

| 验证项 | 验证内容 | 通过标准 |
| --- | --- | --- |
| 扩展抓 URL 能力 | 在目标平台用 `chrome.webRequest` 拦到完整直播流地址与认证信息 | 至少在 1-2 个目标平台跑通 |
| 服务端拉流持续性 | 云端 FFmpeg 拉取直播流，能稳定运行长直播时长 | 连续运行 4-6 小时无中断 |
| 认证态跨网传递 | 扩展抓取的 cookie / header 传到云端发请求能通过身份校验 | 至少在 1-2 个目标平台验证通过 |
| 服务端 IP 风控 | 云端集中 IP 多次拉同一平台直播流，无限速 / 封禁 | 在合理并发数下无显著风控触发 |
| 录制能力剥离评估 | RecordFab 现有 Remux 与结束检测代码能否脱离 CEF 上下文在云端独立编译运行 | 由研发给出可行性结论 |

### 6.2 MVP：形成可评审的最小产品形态

PoC 跑通后，再评估 MVP 是否进入研发排期。MVP 应包含：

- 一个明确入口：按选定路径决定（A1 → 桌面客户端或 Web 控制台；A2 → 浏览器扩展）
- 录制发起：按选定路径决定
- 任务状态：等待中、录制中、完成、失败、文件处理中
- 云端文件库：提供下载、删除、文件保留期
- 通知机制：录制完成和失败通知
- 基础额度规则：限制单用户并发、最长录制时长、文件保留时间

### 6.3 后续自动化能力

以下能力建议在主链路稳定后再讨论（与 A1 / A2 路径选择无关）：

- URL 预约录制：用户保存直播间 URL，到点自动打开并等待直播流。
- 开播时间配置：帮助云端调度资源，降低长时间等待成本。
- 频道 / 主播关注：自动检测开播并录制，复杂度最高。
- 手机 App：作为更完整的跨端控制入口和通知入口。
- 个人云盘同步：作为结果访问增强，而不是云端录制的必要条件。

## 七、主要风险与待验证问题

按"通用风险 / A1 专属 / A2 专属"分层组织。

### 7.1 通用风险（与路径选择无关）

| 风险 | 说明 | 需要验证的问题 |
| --- | --- | --- |
| 直播状态不可控 | 延迟开播、取消、断流、临时下播都可能导致失败 | 状态机和失败提示如何定义 |
| 文件成本 | 直播录制文件体积大，存储和下载都会产生持续成本 | 文件保留期、下载流量、是否计费 |
| 第三方账号安全 | 用户在云端 / 服务端处理第三方网站凭证，需要明确会话和凭据处理方式 | 是否保存账号；是否只保留会话；如何清理 |
| 合规边界 | 服务端代用户录制和保存内容比本地录制更敏感 | 用户协议、平台排除、文件保留策略如何定义 |

### 7.2 A1 路径专属风险

| 风险 | 说明 | 需要验证的问题 |
| --- | --- | --- |
| 云端浏览器成本 | 每路直播录制都占用计算、带宽、存储和可能的代理资源 | 单路成本、并发上限、可承受定价 |
| 长时稳定性 | 直播可能持续数小时，云端浏览器 + 录制器 + 封装 + 存储链路需要长时间稳定 | 浏览器进程稳定性、内存泄漏、像素流断线 |
| 平台风控 | 服务端集中访问 + 虚拟环境浏览器更容易触发风控 | 是否需要代理；代理成本和账号安全边界 |
| DRM / HDCP | 云端虚拟环境可能被平台识别或限制播放 | 目标平台是否能在云端环境播放并录制 |

### 7.3 A2 路径专属风险

| 风险 | 说明 | 需要验证的问题 |
| --- | --- | --- |
| 现有录制能力剥离可行性 | RecordFab 现有 `IRecorder` 与 CEF 强耦合，能否将 Remux / 结束检测等模块脱离 CEF 在云端独立运行需研发评估 | 工程量预估、是否需要重写、可复用比例 |
| 扩展抓 URL 范围 | `chrome.webRequest` 对 HTTP/HTTPS 请求覆盖良好，但对 WebSocket payload、WebRTC 等覆盖有限 | 目标平台直播协议分布；是否存在扩展拦不到流地址的情况 |
| HLS / DASH live 持续拉取 | 直播流是滚动窗口，云端 FFmpeg 长时间拉取的稳定性需要验证 | 4-6 小时连续录制无中断；断流恢复机制 |
| 认证态有效性 | 扩展抓取的 cookie / token 传到云端，可能因 IP 绑定、UA 绑定、时效短而失效 | 哪些平台的 token 可跨 IP 使用；过期续期机制 |
| 服务端 IP 风控 | 云端集中 IP 主动拉流，可能触发目标平台的服务端访问识别 | 不同平台的容忍度；是否需要住宅代理 |
| 多用户并发拉同一平台 | 集中 IP 大量拉流更易触发风控 | 并发上限；代理池策略 |

## 八、待讨论与决策问题

以下问题需在方案评审阶段确认，作为是否进入 PRD、技术 PoC 或研发排期的前置输入。

**首要决策**

- **路径选择**：首期采用 A1 路径（云端浏览器）还是 A2 路径（扩展 + 云端服务）？还是先做 A2 技术可行性调研，再决定是否替代 A1 作为主路径？

**首期范围**

- **首期入口**：PoC / MVP 阶段优先用桌面客户端入口（对应 A1）、Web 控制台、浏览器扩展（对应 A2），还是手机 App？
- **首期功能范围**：首期是否只做"用户进入直播间并点击录制"，暂不做 URL 预约、频道关注和自动开播检测？
- **首期平台范围**：首期验证选择哪些直播平台？是否先选 YouTube Live / Twitch / Kick 等相对典型且无 DRM 的平台？

**技术预研**

- **A2 技术预研**：现有 RecordFab 录制能力（Remux、结束检测、流处理）能否脱离 CEF 上下文在云端环境独立运行？评估周期？
- **A1 技术预研**：云端浏览器、像素流、直播流检测、云端录制、结束判断、文件交付、用户退出后继续录制验证周期？

**商业与合规**

- **商业模型**：云录制按录制时长、录制次数、云录制点数、订阅套餐还是存储套餐计费？失败任务是否扣费？
- **DRM 范围**：A1 是否尝试覆盖 DRM 平台？若 A2 入选，DRM 平台后续是否单独建设？
